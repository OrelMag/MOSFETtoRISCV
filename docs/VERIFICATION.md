# Verification

How the RV32 CPUs are checked, what that found, and what it does not prove. The CPUs and the
instruction-set simulator in `src/riscv/` (the golden model every CPU is co-simulated against) were
written by the same author, so a misreading of the specification shared by both passes every
lock-step test. The checks below do not rely on that model alone.

| Layer | Oracle | Where | In `npm test` |
|---|---|---|---|
| Lock-step co-simulation of the chapters' programs | our golden model | `tests/cpu.test.ts`, `pipeline`, `system`, … | yes |
| **Official riscv-tests** (rv32ui, rv32um, rv32uf, rv32ua, rv32mi) | the tests themselves (self-checking) | `tests/verify-*.test.ts`, `scripts/rvtests.ts` | all of them, every CPU |
| **Random programs** | our golden model, final state | `tests/verify-*.test.ts`, `scripts/fuzz32.ts` | seeds 1–32 per CPU |
| **Coverage** of the two above | — | `tests/verify-*.test.ts`, `scripts/coverage.ts` | no gaps allowed |
| Exported Verilog, synthesized by Yosys | our gate-level simulation | `scripts/verify-export.ts` | CI gate before deploy |

The riscv-tests come from another author, so they check the golden model too: it runs every image,
with each CPU's ISA, before the CPU does.

## Official riscv-tests

[riscv-tests](https://github.com/riscv-software-src/riscv-tests) are self-checking assembly programs:
each writes `1` to the `tohost` word when every case passes, or `(n << 1) | 1` when case `n` fails.
They are built once into images checked in under `tests/verify/riscv-tests/` (one JSON file per
environment, with the source revision and toolchain), so `npm test` needs no RISC-V toolchain.

- **Environments.** `env/p`, the official one (trap vector, `ecall` to report, M-mode CSRs), runs on the
  system CPUs. The other CPUs have no CSRs or traps, so they get `bare`
  (`scripts/riscv-tests/env/bare`): the same test bodies and the same `tohost` contract, with a store
  and a jump-to-self instead of `ecall`. `bare-mp` adds env/p's `csrr mhartid` park so hart 1 of the
  dual-core waits while hart 0 runs the test.
- **Harvard memory.** Code is linked at 0 (the ROM), data at `0x10000`, which is word 0 of any data
  memory up to 16 K words (it wraps), with `tohost` first. Our CPUs have no loader, so the image gets a
  few instructions appended (`lui` / `addi` / `sw` per non-zero data word, encoded by hand rather than by
  our assembler) and its reset jump at address 0 is retargeted through them. ROM and RAM are sized per
  test (`imemK`, `dmemK` on every CPU generator).
- **Running.** Up to 32 tests run at once on one CPU build: BitSim evaluates the instruction ROM per
  lane (`setLaneBehavior`), one program per lane, every other leaf a NAND. Each CPU runs every test
  its ISA covers within a cycle budget (golden-model instructions × the CPU's worst CPI), and the
  harness reads `tohost` from the data memory (through the cache's dirty lines where there is one).
  `tests/rvtests.test.ts` checks a few runs against the event-driven simulator.
- **Not applicable** is decided from each CPU's declared ISA, never from results (reasons below the
  matrix). `ld_st` and `st_ld` pass on a word-only CPU too, since every value they store is
  sign-extended, so they count as byte / halfword tests rather than as evidence.

To rebuild the images (a new riscv-tests revision): clone riscv-tests with its `env` submodule, get a
GNU RISC-V toolchain (`riscv64-unknown-elf-gcc`, or xPack's `riscv-none-elf-gcc` on Windows; clang's
assembler rejects a few GNU-isms in the sources), and run
`node scripts/riscv-tests/build.mjs <riscv-tests> --cc <gcc>`. The build is deterministic.

## Random programs

`src/riscv/randprog32.ts` draws a program from a seed for what a CPU implements: ALU operations on
edge values (0, ±1, `INT_MIN`, `INT_MAX`, shift amounts 0 / 31), every branch, `jal`, `jalr`, short
counted loops (backward branches, so predictors learn and mispredict), loads and stores of every width
the CPU has (base + offset, or an address computed from data), M with division by zero and overflow,
F with zeros, infinities, quiet and signalling NaNs, subnormals and every rounding mode, `fcsr`
access. On the system CPU: CSR reads and writes, `ecall`, `ebreak`, illegal words, misaligned loads,
stores and jumps (a handler skips them) and a timer interrupt. On the dual-core: `amoadd.w`,
`amoswap.w`, `csrr mhartid` on shared memory. Sources are drawn from the last few destinations more
than half the time, so forwarding, load-use stalls and branches right after loads are everywhere.
Every path is forward or a bounded loop, so every program halts.

Thirty-two programs run at once (one per lane). A lane stops once its fetch reaches the final
jump-to-self, plus 64 cycles for what is in flight. Its final registers, FP registers, `fcsr` and
data memory must equal the golden model's (for the dual-core, the multi-core model with the same
arbitration). On a mismatch the program is replayed alone, in lock-step on the event-driven simulator,
comparing the retiring PC and the registers at every retirement; the failure reports the seed, that
first difference and the program.

`npm test` runs seeds 1–32 on every CPU. `npx vite-node scripts/fuzz32.ts [cpus] --seeds 1..10000
--out failures.json` runs any range; the scheduled workflow `.github/workflows/verify.yml` runs a new
range every night and keeps the failures as an artifact.

from the golden model's runs of the same programs; hardware events are read from each CPU's own nets
every cycle (hazard-unit forwarding selects, stall and flush lines, the misprediction detector, cache
hit and stall lines, the write-back controller, the CSR unit's trap and interrupt lines, the
multicycle controller's state). The `npm test` suites fail if an instruction a CPU claims is never
executed or an event it has is never seen. `fence` and `wfi` are not counted: they do nothing here.

## What this found

| Where | Bug | Found by | Fix |
|---|---|---|---|
| Golden model | `slli` / `srli` / `srai` with `instr[25]` set (the RV64 `shamt[5]`) executed instead of trapping; the system CPU's decoder was right | rv32mi `shamt` | decode compares the whole `funct7` |
| Golden model and system CPU | `mvendorid`, `marchid`, `mimpid` trapped; they are mandatory (may read 0) | rv32mi `mcsr` | three read-only zero CSRs in both |
| Pipelined RV32IM | `div` / `rem` with forwarded operands of changing sign gave the wrong sign: the divider latched the magnitudes at start but fixed the sign from the live operands at the end, which by then were stale register values (the producers drained out of M / W during the stall) | rv32um `div`, `rem` | signs latched with the magnitudes |
| Pipelined RV32IF | a taken branch in E while D waited on an FP interlock lost its target: the stall held the PC that the branch had to load | random programs (5 of 256 seeds) | PC enable = not stalled, or taken |
| I-cache generator | the instruction cache assumed a 64-word ROM, so a larger program aliased in its tags | riscv-tests (larger images) | sized from the ROM |

Each fix came with a failing test first (`tests/pipem.test.ts`, `tests/fppipe.test.ts`, the
riscv-tests suites).

## What this does not prove

- **The random programs still use our golden model as the oracle**, at the final state. They catch the
  hardware disagreeing with the model, not both sharing a misreading. A second, independent model
  (Spike or Sail) comparing commit logs on the same programs is the next step (docs/ROADMAP.md, Phase 13).
- **`bare` is our environment.** The test bodies are the official ones; the code around them (start,
  pass / fail reporting) is ours, as env/p's would be on any core without traps.
- **Features we do not claim are not tested**: byte / halfword access outside the system CPUs,
  misaligned access in hardware, `fence.i` and self-modifying code (the ROM is read-only), atomics
  beyond `amoswap.w` / `amoadd.w`, PMP, debug triggers, `instret`. The matrix lists them as n/a.
- **Coverage counts what happened, not what matters.** Every forwarding path firing does not mean every
  combination of hazards met; seeds beyond 32 (the nightly run) widen that.
- **The CPU's timing is not checked here**: cycle counts are only bounded by a budget, and the gate
  delays are the same unit model as everywhere else.
